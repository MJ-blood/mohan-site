前后端由不同 Agent 负责时，我想减少自己在中间复制问题、代码和进度的工作。为此，我先要解决一个更基础的问题：什么状态才算已经交接？

“已经修改”可能只是工作区发生了变化，“已经提交”可能仍然只在本机。“对方可以开始核对”还需要更多条件。把这些状态混在一起，后面的验证就容易失去依据。

## 交接要能指向具体版本 {#version}

我把已推送的远端任务分支与 commit SHA 定为正式交接依据。分支负责指向这项工作，提交标识负责确定这次交接的具体版本。

接收方读取以后，才能明确说出自己检查了什么；发现问题时，也能把证据归到这个版本。换一台机器，交接对象仍然存在，不依赖某个还没有同步的工作区。

> 一次交接，应该让接收方知道：读哪个版本、核对什么、把结果记在哪里。

本机有对方仓库，可以方便读取；但先核对仓库身份，再读指定提交。固定路径只能说明文件可能放在哪，不能承担项目身份和同步依据。

## 一个问题，要有连续的身份 {#ownership}

接下来是责任。发现问题的 Agent 不一定负责修复它。我让发现方登记问题 ID、证据和责任仓，接收方沿用同一个 ID，修复后回填对应提交。

当责任方接收问题后，发现方不再维护完整的问题正文，只保留指向权威记录的引用。否则两边都更新，很快就会出现两份不一致的“当前状态”。

每个 Agent 只写自己的仓。跨仓协作依靠明确的交接材料和读取动作完成，不能因为能够访问对方仓库，就顺手替对方修改代码。

无法判断责任时，则停在“待定责”，由人决定。一个模糊的问题在两个仓之间反复移动，并不会因为移动次数增加而变清楚。

## 把流程授权说到具体动作 {#permission}

这份协议还有一层边界：允许联调、继续已有任务、批准合并，分别是不同动作。确认某一步，不代表把后面的每一步都交给 Agent 自行决定。

工作流中的“只读”也需要如实理解。它是执行纪律，不能伪装成技术权限隔离。如果需要强制限制，就必须由权限或其他机制承担。

这套流程仍然需要人触发接续，也有记录和维护成本。只有一个写入者的小任务，不需要照搬全部规则。多个仓、多个写入者、跨设备恢复同时出现时，明确这些事实才有足够的价值。
